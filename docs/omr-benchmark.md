# Бенчмарк движков OMR (2026-10-30)

Цель — выбрать движок распознавания нот. Главный критерий (см. ROADMAP, «Приоритеты»): такт после загрузки **выглядит на экране как в оригинале** — ноты, длительности, связующие и фразировочные лиги. Режим игры на выбор не влияет.

Код и запуск: `services/omr-worker/bench/` (`prepare_reference.py`, `run.py`, `compare.py`, `report.py`, `review.py`), набор — `bench/dataset.yaml`. Ноты, фото и результаты в git не входят.

## Набор

|---|---|---|

Все фото — 960×1280 (сжаты мессенджером), оригиналов нет.

## Наблюдения

- homr выдаёт связующие лиги как фразировочные: 52 из 57 его дуг на страницах Джоплина стоят между двумя одинаковыми нотами. На экране дуга видна, но MusicXML неверен. Нужна постобработка: дуга ровно между двумя нотами одной высоты → связующая лига.
- Размер такта печатается только на первой странице; движки видят страницы по отдельности, поэтому проверка применяет размер с первой страницы ко всем следующим (так будет и в приложении после склейки страниц).
- Если засчитывать такт только при согласии Audiveris и homr, неверных незамеченных тактов становится 4 % (вместо 10 % у одного Audiveris), но подозрительными помечаются 28 % тактов.
- music21 теряет фразировочные лиги при чтении Humdrum, поэтому их эталон взят из MEI Verovio.

## Решение

Задача — распознать ноты с картинки, показать их по тактам в едином виде, позже сверять с ними игру по MIDI. Для неё важнее всего высоты, длительности и связующие лиги.

- **homr — единственный движок** для фото и PDF (PDF растеризуется). По нотам он почти равен Audiveris (82 % против 85 % тактов), на фото работает только он, в 2 раза быстрее и без Java. Лиги исправляются постобработкой: дуга между двумя одинаковыми нотами → связующая лига.
- **Audiveris** — возможный запасной движок для чистых PDF; на фото не справился даже после увеличения в 2 раза.
- **oemer отклонён.**
- homr под AGPL-3.0 — запуск без модификаций, юридическая проверка перед публичным запуском. Пути улучшения — ARCHITECTURE §7.4.

## Ограничения

Набор маленький: результат — ориентир для выбора, а не статистика. Эталонные PDF нарисованы программой (лучший случай); реальные PDF и фото пользователя распознаются хуже, насколько — покажет ручная сверка (`python -m bench.review`).
