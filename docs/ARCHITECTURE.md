# Архитектура

> Рабочее название: **piano-trainer** (кандидаты: NoteQuest, Piece by Piece, My Repertoire).
> Описание идеи: [IDEA.md](./IDEA.md). План работ: [ROADMAP.md](./ROADMAP.md).

## 1. Ключевые принципы

1. **Offline-first.** Разучивание, режим игры, прогресс и стрики работают без сети. Источник правды для MVP — SQLite на устройстве. Сервер нужен только для OMR, а позже для аккаунта и синхронизации.
2. **Музыкальная логика — чистый TypeScript без UI.** Парсинг партитуры, сопоставление сыгранных нот, оценка попытки, статусы фрагментов, интервальное повторение и сборка урока живут в `packages/*`. Они не зависят от React Native и покрываются юнит-тестами.
3. **Критичное по времени уходит в натив.** MIDI-события получают метку времени в нативном коде, а метроном и воспроизведение планируются на аудио-часах (не на `setTimeout`).
4. **Нотный стан — «глупое» представление.** WebView с Verovio только рисует и подсвечивает. Решения о том, правильная ли нота, принимает `practice-engine` в JS-потоке приложения.
5. **Схема данных сразу готова к синхронизации:** UUIDv7, `updatedAt`, `deletedAt` (мягкое удаление), попытки хранятся как append-only журнал.

## 5. Модель предметной области

### 5.1 Партитура

Хранятся три представления:

1. **Исходник:** файл пользователя (PDF, фото, MusicXML, MXL). Лежит в файловой системе устройства, для OMR ещё и в S3.
2. **Каноническая партитура:** MusicXML, а после первой загрузки в Verovio ещё и **MEI** со стабильными `xml:id`. Именно MEI рендерится, и на него ссылаются ID нот.
3. **`PracticeScore`:** плоский JSON-индекс для движка, строится один раз при импорте и кэшируется в БД:

```ts
PracticeScore {
  measures: { index, number, timeSig, startQ, durationQ }[]
  notes:    { id /* = xml:id в MEI */, midi, staff /* 1 = правая, 2 = левая */,
              measureIndex, onsetQ, durationQ, tieContinuation, grace }[]
  tempoBpm: number
}
```

`Q` — позиция в четвертях от начала (qstamp из timemap Verovio). Ритм хранится в долях, а не в мс, поэтому смена темпа — это просто пересчёт.

> ⚠️ **Проверяется в спайке:** как надёжнее получить `staff` и `xml:id` для каждой ноты — парсить экспортированный Verovio MEI или опрашивать toolkit (`getElementAttr`, `getMIDIValuesForElement`). Повторы и вольты в MVP не разворачиваются: играем линейно, по тактам.

### 5.2 Сущности (SQLite на устройстве, позже такие же в Postgres)

| Таблица | Поля (основные) |
|---|---|
| `pieces` | id, title, composer, coverUri, sourceKind (`musicxml`/`mxl`/`omr`), scorePath (MEI), practiceScoreJson, measureCount, unscoredMeasures (JSON-массив индексов тактов, см. §7.3), createdAt, updatedAt, deletedAt, lastPracticedAt |
| `fragments` | id, pieceId, measureStart, measureEnd, order, status, createdAt, updatedAt |
| `attempts` | id, fragmentId, hands (`R`/`L`/`RL`), mode (`wait`/`tempo`), tempoPct, noteAccuracy, rhythmAccuracy, missed, extra, durationMs, passed, createdAt (append-only) |
| `review_schedule` | fragmentId, dueAt, intervalDays, ease, lapses, consecutivePasses |
| `lessons` | id, date (локальная дата), plan (JSON), completedAt |
| `streak_days` | date (локальная дата, PK), lessonId |
| `settings` | key, value (фрагмент по умолчанию N тактов, задержка MIDI, устройство и т. п.) |

Статус произведения не хранится, а **вычисляется** из статусов фрагментов (доля выученных, наличие требующих повторения).

### 5.3 Статусы фрагмента

```
not_started ──первая попытка──► learning ──критерий освоения──► learned
                                   ▲                              │ наступил dueAt
                                   │ провал при повторении        ▼
                                   └─────────────────────── needs_review ──успех──► learned (интервал ↑)
```

Критерий освоения (настраивается): **3 попытки подряд с точностью нот ≥ 95 % в режиме в темпе при темпе ≥ целевого**. Пока режим в темпе не готов, засчитывается режим ожидания без ошибок.

Интервальное повторение: упрощённый SM-2 с интервалами 1 → 3 → 7 → 14 → 30 дней, при ошибке интервал сокращается, растёт `lapses`. Алгоритм спрятан за интерфейсом `Scheduler`, чтобы позже заменить его на FSRS.

## 6. Режим игры: главный технический узел

> **Не приоритет** (ROADMAP, «Приоритеты»): сейчас главное — загрузка и отображение нот. Решения по распознаванию и отображению к режиму игры не привязываются; раздел описывает отложенную часть.

### 6.1 Поток данных

```
Клавиша ─► CoreMIDI / MidiManager ─► expo-midi (нативная метка времени, нс)
        ─► JS: NoteEvent {type, midi, velocity, tNative}
        ─► clock.toSessionTime(tNative)            // общая шкала с аудио-часами
        ─► practice-engine.matcher.feed(event) ─► MatchResult[]
        ─► notationBridge.highlight(ids, color)  ─► WebView (Verovio SVG)
        ─► session store (Zustand) ─► UI счётчиков
```

### 6.2 Режим ожидания (`wait`)

- Ожидаемая последовательность — **группы одновременных нот** (одинаковый `onsetQ`) выбранных рук; продолжения лиг и форшлаги пропускаются.
- Группа засчитана, когда все её высоты нажаты (порядок любой, допустимое окно между нотами аккорда около 150 мс), после этого курсор переходит дальше.
- Чужая нота: красная подсветка и счётчик ошибок, курсор стоит на месте.
- Когда сыграна последняя нота фрагмента, выдаётся событие `fragmentCompleted`, UI листает дальше.

### 6.3 Режим в темпе (`tempo`)

- Ожидаемое время ноты: `tStart + onsetQ × 60 / (bpm × tempoPct)`.
- Сыгранная нота сопоставляется с ближайшей ожидаемой той же высоты в окне ±(допуск); жадно с откатом (score following), без глобального DP в MVP.
- Классы: `correct` (вовремя), `early` и `late` (правильная высота вне окна «хорошо», но в окне «засчитано»), `wrong` (нет такой высоты рядом), `missed` (окно ожидаемой ноты истекло).
- Допуски задаются в долях бита (например, «хорошо» ±1/8, «засчитано» ±1/4), чтобы на медленном темпе они не были слишком строгими.
- Перед стартом идёт отсчёт метронома (1 такт).

В обоих режимах ноты тактов из `unscoredMeasures` не оцениваются: их можно сыграть как угодно, ошибки не считаются, курсор просто проходит такт (§7.3).

### 6.4 Время и задержки

- Все времена переводятся в одну шкалу: аудио-часы `AudioContext.currentTime` ⇄ нативные метки MIDI. Модуль `services/audio/clock.ts` хранит смещение и периодически его пересинхронизирует.
- **Калибровка задержки:** в настройках пользователь стучит в такт метроному, считается среднее смещение (BLE MIDI добавляет 10–30 мс). Смещение вычитается из меток MIDI.
- Задержка подсветки (JS → WebView) не влияет на оценку: оценка идёт по нативным меткам, а не по моменту отрисовки.

### 6.5 Мост с WebView (`packages/notation-view`)

- Бандл (Vite → один HTML с inline JS и WASM Verovio) лежит в ассетах приложения и работает офлайн.
- Протокол — типизированные сообщения JSON (`protocol.ts` используют обе стороны):
  - RN → Web: `load {mei}`, `showRange {fromMeasure, toMeasure, staves}`, `highlight {ids, state}`, `clearHighlights`, `cursor {ids}`, `setTheme`.
  - Web → RN: `ready`, `loaded {pageCount, timemap, notes}`, `rendered {range}`, `error`.
- Разделение рук: Verovio рисует только выбранные нотоносцы (через `select`/фильтрацию MEI в `score-core` перед загрузкой).
- Подсветка — переключение CSS-классов у `g#<xml:id>`, без перерисовки SVG.

### 6.6 Отладка без пианино

- **Экранная клавиатура** (только в dev-сборке) отдаёт такие же `NoteEvent`, как MIDI.
- **Воспроизведение MIDI-файла как ввода** — фикстуры для тестов `practice-engine` («сыграно идеально», «сдвиг на 80 мс», «пропущен аккорд»).

## 7. Оцифровка нот (OMR)

### 7.1 Поток

```
клиент: 1 PDF или 1–10 фото ─► POST /v1/omr/jobs (multipart) ─► job {status: queued}
api: файлы в FileStorage, запись в JobRepository, задача в JobQueue
worker: взять задачу ─► предобработка: PDF→PNG (PyMuPDF, 300 dpi), фото — поворот по EXIF, HEIC→PNG
        ─► homr по страницам (прогресс после каждой) ─► склейка страниц в одну партитуру
        ─► проверка тактов (§7.3) ─► result.musicxml + report.json ─► status=done | failed
клиент: GET /v1/omr/jobs/:id/events (SSE) или опрос GET /v1/omr/jobs/:id
        ─► скачать result.musicxml ─► экран результата ─► импорт
```

- **Связь с клиентом — REST + SSE.** Сервер отправляет только статус и прогресс, клиент своё делает обычными запросами (создать, отменить, скачать), поэтому двусторонний WebSocket не нужен. SSE — обычный HTTP: проходит через прокси, сам переподключается, проверяется `curl -N`. Если поток недоступен, работает опрос `GET`.
- **Файлы загружаются прямо в API** одним multipart-запросом: так можно тестировать в Swagger. Presigned upload в S3 для мобилки можно добавить позже, остальной код не изменится.
- **Ограничения:** 1 PDF до 20 страниц или 1–10 фото (JPEG, PNG, HEIC) одной композиции, файл до 25 МБ. Тип файла определяется по содержимому, а не по расширению.

### 7.1.1 Локальный режим без Docker

Хранилище, база задач и очередь спрятаны за интерфейсами (`FileStorage`, `JobRepository`, `JobQueue`). Сейчас есть только локальная реализация, на сервере её заменят S3, Postgres и BullMQ:

```
Swagger ──► api (NestJS) ──► .data/omr/omr.sqlite (таблица omr_jobs) ◄── omr-worker (опрос раз в 1 с)
               └──────────► .data/omr/jobs/<id>/   (исходники, страницы, результат) ◄──┘
```

- Очередь — сама таблица: воркер атомарно переводит самую старую задачу `queued` в `processing` и пишет в ту же запись прогресс и результат.
- SSE: API раз в 0,5 с перечитывает запись и отправляет событие, если она изменилась.
- Отмена: задача в очереди отменяется сразу; у задачи в работе API ставит флаг, воркер проверяет его каждые 0,5 с и останавливает homr.
- Задачи, оставшиеся в `processing` после падения воркера, при его запуске получают `failed` с кодом `interrupted`.

### 7.2 Движки и лицензии

Выбор сделан по бенчмарку ([omr-benchmark.md](./omr-benchmark.md)). Задача: распознать ноты с картинки (фото, скриншот, страница PDF), показать их в едином виде по тактам, а позже сверять с ними сыгранные по MIDI ноты. Поэтому главное — верные высоты, длительности и связующие лиги; фразировочные лиги — оформление.

- **homr 0.7** (AGPL-3.0, Python) — **единственный движок**. Ноты и длительности верны в 82 % тактов эталонных PDF (у Audiveris 85 %) и в 38 из 38 тактов на снимках экрана; ~30 с на страницу. PDF растеризуется и распознаётся так же, как фото. Связующие лиги homr выдаёт как фразировочные — исправляется постобработкой (§7.4), поэтому «как в оригинале» на PDF пока лишь 45 % тактов.
- **Audiveris 5.11** (AGPL-3.0, Java) — возможный запасной движок для чистых PDF, если по ним будут жалобы: с лигами точнее (73 % тактов как в оригинале), но в 2 раза медленнее, нужна Java, а на фото не работает даже после увеличения в 2 раза (на снимках экрана нашёл 11 и 3 такта из 19). Адаптер в воркере уже есть, включая склейку частей `mvt1`, `mvt2`….
- **oemer** (MIT) — отклонён: 15 мин на страницу и ошибки с первого такта, не обновляется с 2025 года.
- Абстракция `OmrEngine` позволяет подключить другой движок без изменений в остальном коде.
- homr под AGPL: запускаем отдельным процессом **без модификаций**; если менять его код или модель и запускать на сервере, изменённый код придётся опубликовать. Перед публичным запуском — юридическая проверка.
- **Verovio** — LGPL-3.0: подключаем без изменений как отдельный WASM-модуль в WebView, лицензию указываем в «О приложении».

### 7.3 Проверка качества вместо редактора

В MVP **нет ручного редактора нот** (перенесён в «После MVP»). Ошибки распознавания не исправляются; приложение находит подозрительные такты и честно показывает их на экране.

- Пустые нотоносцы (заготовки без нот) закрашиваются до распознавания, страница без нот не считается ошибкой, такт без нот и пауз удаляется при склейке (`omr_worker/empty_staves.py`, `merge.py`): такие такты не попадают в партитуру и в подсчёт качества.
- Проверка находит подозрительные такты: сумма длительностей по голосу ≠ размеру, событие выходит за конец такта, такта нет на одном из нотоносцев, пустой такт, неизвестен размер. Размер, напечатанный только на первой странице, действует на всех следующих. Если движок не нашёл знак размера, размер вычисляется по самой частой длине такта без первого и последнего (нужно не меньше 4 тактов и не меньше 60 % с одной длиной) и помечается в отчёте как `inferred`.
- Для OMR проверку делает воркер (`omr_worker/measures.py`, её же использует бенчмарк) и кладёт результат в `report.json` с причинами по каждому такту. `score-core.validateMeasures()` на TS появится вместе с импортом MusicXML в приложение (фаза 2) и должна давать тот же результат.
- Индексы подозрительных тактов записываются в `pieces.unscoredMeasures`; при отображении такие такты помечаются («возможна ошибка распознавания»). (Не приоритет: в режиме игры они не оцениваются, §6.)
- **Порог:** если нормальных тактов меньше 40 % (`OMR_MIN_OK_RATIO`), задача завершается `failed` с кодом `low_quality`: «Не удалось надёжно распознать, попробуйте PDF лучшего качества или файл MusicXML». MusicXML и отчёт при этом всё равно можно скачать — для отладки.
- Экран результата: превью нот с помеченными тактами, кнопки «Добавить в библиотеку» и «Отмена».
- Проверка работает для любого источника, в том числе для импортированного MusicXML.

### 7.4 Как улучшать распознавание

Каждое изменение проверяется на бенчмарке (`services/omr-worker/bench`: `run.py` → `report.py`) — видно, стало лучше или хуже.

1. **Постобработка результата** (наш код в воркере, AGPL не затрагивает):
   - дуга ровно между двумя нотами одной высоты → связующая лига;
   - размер такта с первой страницы действует на следующих;
   - склейка страниц в одну партитуру;
   - пометка подозрительных тактов (§7.3).
2. **Подготовка картинки** (наш код): обрезка по краю листа, исправление перспективы и изгиба страницы, контраст и бинаризация, увеличение мелких изображений. Главный резерв для сжатых фото и PDF с картинками низкого разрешения.
3. **Доработка модели homr** (дообучение на своих данных, например на типичных фото пользователей) — последним шагом: сложно, и изменённый код homr при серверном использовании придётся опубликовать (AGPL).

## 8. API (MVP)

Swagger UI — `/docs`, схема OpenAPI — `/docs-json`. Схемы ответов описаны на zod в `packages/contracts` и оттуда же попадают в Swagger.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/v1/health` | Живость |
| POST | `/v1/omr/jobs` | multipart `files`: 1 PDF или 1–10 фото по порядку страниц → задача `queued` |
| GET | `/v1/omr/jobs` | Последние задачи |
| GET | `/v1/omr/jobs/:id` | Задача: статус, прогресс, страницы, результат или ошибка |
| GET | `/v1/omr/jobs/:id/events` | SSE: `progress` при каждом изменении, в конце `done`, `failed` или `cancelled`; в `data` — вся задача |
| POST | `/v1/omr/jobs/:id/cancel` | Отмена |
| GET | `/v1/omr/jobs/:id/result.musicxml` | Скачать результат (есть при `done` и при `failed` с `low_quality`) |
| GET | `/v1/omr/jobs/:id/report.json` | Отчёт по тактам |
| GET | `/v1/omr/jobs/:id/pages/:page` | Страница после предобработки (PNG) |

Статусы задачи: `queued → processing → done | failed | cancelled`. Коды ошибок: `low_quality`, `unreadable_file`, `too_many_pages`, `no_music_found`, `engine_failed`, `timeout`, `interrupted`. Ошибки запроса (400) — `{code, message}`: `no_files`, `unsupported_file_type`, `mixed_sources`, `too_many_files`, `file_too_large`.

В MVP вместо аккаунта используется **анонимный device token**: rate limit на OMR и привязка задач. Позже появятся `auth` (Sign in with Apple / Google / email-ссылка) и `sync` (push/pull изменений по `updatedAt`, попытки — только append).

## 10. Качество

- **Юнит-тесты** — основной упор: `score-core` (фикстуры MusicXML: аккорды, лиги, форшлаги, смена размера) и `practice-engine` (фикстуры сыгранных последовательностей).
- **Контрактные тесты** API на zod-схемах.
- **E2E (Maestro):** импорт MusicXML, открыть фрагмент, сыграть его через экранную клавиатуру, увидеть результат.
- **Ручной чек-лист железа:** USB-MIDI на iOS (через переходник Lightning/USB-C) и Android (OTG), BLE MIDI на обеих ОС, переподключение, сворачивание приложения.
- CI: lint, typecheck и test по затронутым пакетам (`turbo --affected`), EAS Build на тегах.

## 11. Риски

| Риск | Чем снимаем |
|---|---|
| Verovio в WebView тормозит на больших партитурах | Рендер только диапазона тактов (`select`), кэш SVG по фрагментам |
| Задержка BLE MIDI и разброс по Android-устройствам | Нативные метки времени, калибровка, допуски в долях бита |
| Нестабильная точность OMR | Импорт MusicXML с первого дня, пометка подозрительных тактов, порог отказа, постобработка и подготовка картинки с проверкой на бенчмарке (§7.4) |
| AGPL homr | Отдельный процесс без модификаций, юридическая проверка; улучшения — в нашем коде вокруг движка |
| Повторы, вольты, многоголосие в одной руке | MVP: линейное воспроизведение; голоса внутри нотоносца уже учитываются в `PracticeScore` |
| Авторские права на ноты | Только пользовательские файлы в MVP, без общего каталога |
